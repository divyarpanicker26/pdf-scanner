Design document

Browser-based replacement for PSIGEN

Prepared by Divya Radhakrishnan · October 2026 · Status: working prototype

1. Purpose

NYCHA processes inbound documents in PSIGEN. PSIGEN is a licensed product that must be installed on each computer, and a license limits how many people and machines can use it. Adding a person or a workstation means another install and another license.

This document describes a browser tool that does the same intake job without an install and without a license. Staff open a PDF, name the fields they need, and receive those values as structured data they can check and copy. Annual recertification is the worked example. The tool is not limited to that process.

2. Problem

Inbound documents arrive from residents, applicants, vendors, and partners, often as PDFs or scans. Staff use PSIGEN to read them and move the facts into the system of record.

  • PSIGEN must be installed on every computer that uses it.
  • A license caps how many people and machines can use it. When the licenses are used up, the next person or office waits.
  • Updates are applied to each installation.
  • Staff can work only on machines where PSIGEN is set up.

The prototype does not yet replace every PSIGEN feature. Scanning hardware, exports, and other features staff rely on still need to be listed with the people who use PSIGEN today.

3. Goals and non-goals

Goals

  • Read a PDF in the browser and return named fields as structured data.
  • Let staff define a field setup per document type, without a developer.
  • Show the original page so staff can check each value before it is used.
  • Keep the document on the computer. Do not upload it.
  • Run from a web address, with nothing to install and no license to assign.

Non-goals for this prototype

  • Connecting to a NYCHA system of record. Staff still paste checked values in.
  • Deciding eligibility, calculating rent, or approving a case.
  • User accounts, roles, or an audit trail.
  • Replacing PSIGEN features that have not been compared yet, such as scanning and exports.

5. What the prototype does

The staff member drops a PDF on the page or chooses a file. The tool reads every page, shows a preview of the first six pages, and fills in the fields. The result is JSON the staff member can copy or download. A field the tool cannot find is marked missing rather than left blank without notice.

Three fictional sample packets are built in, so the flow can be shown without real tenant data:

  • Annual recertification of family income and composition.
  • Affidavit of income.
  • Declaration of assets.

Opening one of those samples also loads the matching field list. Other inbound documents use the same screen. A person adds the labels for that document type. Candidate processes, still to be confirmed with each business area, include applications, income and benefit proof, household change requests, vendor paperwork, and resident correspondence.

The samples are marked “not an official NYCHA form.” The household, account number, income, and balances are fictional.

6. How a document is read

Reading happens entirely in the browser. There is no application server.

  1. The file must be a PDF and must be 25 MB or smaller. A password-protected PDF is rejected with a message to remove the password.
  2. Each page is read with PDF.js. Text items are ordered into lines by their position on the page.
  3. If a page has almost no text (fewer than 25 non-space characters), that page is treated as a scan. It is drawn to an image and read with English OCR (Tesseract.js). The first OCR run downloads the English language data.
  4. Pages are joined into one text block. The result records whether OCR was used.
  5. A JPEG preview is kept for the first six pages. Later pages are still included in the extraction.

7. How a field is found

Each field has a JSON key, a label as printed on the document, an optional regular expression, and a flag for values that continue onto the next lines. The address on the recertification sample is the multiline case: three printed lines become one value.

RuleBehavior
LabelThe line must start with the label, then an optional colon or hyphen, then the value. Matching ignores letter case.
Value on the next lineIf the label line has no value, the next non-empty line is used.
MultilineFollowing lines are kept until a blank line or another label. They are joined with commas.
Regular expressionWhen a pattern is set, it replaces the label rule. The first capture group is the value. If there is no capture group, the whole match is used.
ErrorsAn empty key, a repeated key, an invalid pattern, or a field with neither a label nor a pattern is reported on that field. A value that is not in the document is returned as missing.

Field setups are remembered in that browser only (localStorage). The document and the extracted values are not saved. “Restore suggested” clears the saved setup and returns the default five fields: name, case number, address, income, and document date.

Built-in setups, loaded with the samples:

DocumentFields
Annual recertificationName, case number, account number, development, address, household size, income, document date
Affidavit of incomeName, case number, address, employer, gross wages, SSI amount, public assistance, income, document date
Declaration of assetsName, case number, address, bank name, account type, checking balance, savings balance, document date

8. System design

The prototype is a single-page application. The browser is the whole runtime.

PieceRole
React pageFile drop, field editor, preview, JSON result, copy, and download.
PDF.jsOpens the PDF, reads the text layer, and draws page previews.
Tesseract.jsEnglish OCR for pages that have almost no text.
Field extractorApplies the label and pattern rules to the page text. Covered by unit tests.
Vite buildProduces a static site. Relative paths so it can be hosted in a subfolder.

There is no database, no login, and no API. A future NYCHA deployment would still be a static site, hosted where IT approves, until a later phase adds a connection to a system of record.

10. Privacy and security

Today the PDF is read in the browser and is not sent to a server. Extracted values are not stored. Only the field setup is stored, and only in that browser.

That is not yet enough for real tenant, applicant, or vendor documents.

  • Host the page on NYCHA-approved infrastructure. The public GitHub Pages site is for demos with fictional samples only.
  • Bundle the OCR language files with the site. Today the first OCR run downloads them from the internet.
  • Complete an IT security and privacy review before a pilot with real documents.
  • A later phase that writes into a system of record will need accounts, access control, and an audit trail. Those are out of scope for the prototype.

11. Limits

  • Tested on fictional recertification samples, not on real NYCHA documents or on a PSIGEN export.
  • Values are found by a label at the start of a line, or by a regular expression. A form laid out as boxes, columns, or handwriting will need a different setup, and some layouts will not extract reliably.
  • Each new document type needs its own field list, then a check against real samples.
  • OCR is English only and is not reliable on handwriting.
  • There is no side-by-side feature comparison with PSIGEN yet. Scanning, batch intake, and exports are examples of features still to confirm.
  • Staff still paste values into the system of record. The tool does not file the document or update a case.

12. Proposed pilot

One office and a few staff. Start with recertification, because those field setups already exist. Then add one document type from another process, to show that a new form is a new field list rather than a new system.

Staff run the same documents through PSIGEN and the browser tool. Measure:

  • Minutes per document, compared with PSIGEN.
  • Share of fields extracted correctly, compared with PSIGEN.
  • How often staff had to correct a value.
  • How long it takes to set up a new document type.
  • Whether staff can complete the work without an install or a license.

The pilot uses approved hosting and real forms only after the security review. At the end, leadership decides whether to start replacing PSIGEN, adjust the tool, or stop.

13. Open questions

  1. Which PSIGEN features do staff rely on besides reading a PDF and copying fields? Scanning, batches, and exports need a list from current users.
  2. What is the actual license limit: named users, concurrent users, or machines? The design treats it as a cap. The number is not in this document.
  3. Which inbound document types, after recertification, cost the most staff time?
  4. Where should a production copy be hosted, and may OCR language data be bundled so the browser never downloads it?
  5. If a later phase writes into a system of record, which system, and who confirms a value before it is saved?
